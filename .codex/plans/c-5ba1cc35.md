# Codex plan for mehrangta/funny-whiteboard-paint#8

Job: `c-5ba1cc35` · Revision: 1

Decision-ready implementation plan grounded in the current Vite/TypeScript + Tauri repository. The existing app renders directly into one responsive canvas, stores PNG data URLs in Rust-global undo/redo stacks, and reads/writes basename-only PNG files under the app-data saved_images directory. The plan replaces that raster state with a versioned document model and frontend document history, preserves PNG export, and treats imported PNG content as non-selectable background data. No files were modified. The draft assumes the recommended answers to the material questions below.

## Risks

- Long brush paths and embedded PNG payloads can make JSON documents and history snapshots memory-heavy; avoid raster snapshots, deduplicate only redundant path samples, enforce documented file/geometry validation limits, and keep the existing 50-history-entry cap.
- Text bounds depend on platform font metrics. Use a fixed schema font token mapped to the current system-sans stack, load fonts before measurement when possible, and use the same measurement/rendering path for hit testing and PNG export.
- Canvas display size, document dimensions, and devicePixelRatio are currently conflated. The renderer and all pointer/hit-test code must consistently use the document-to-viewport transform or selection and export will drift after resize.
- A project can be valid JSON while containing corrupt or oversized embedded PNG data. Rust must validate the decoded PNG before accepting the document, and opening must remain transactional until the frontend has decoded required images.
- Native path access expands the backend boundary beyond the current app-data basename restriction. Keep file selection user-driven, validate extensions and file kinds in Rust, and grant only the dialog permissions required by the main window.
- Flattened legacy PNGs cannot be reconstructed into editable objects. Compatibility is intentionally limited to importing the whole image as a locked background; document this clearly and do not imply automatic vector recovery.
- The issue's editing scope, file-location workflow, and PNG background semantics materially affect UI and implementation size. The plan is complete under the recommended options but should be adjusted before implementation if different answers are selected.
